## ADR-0008 — Holdings 티커 입력 UX: 티커 디렉토리(캐시) + 검색/최근 후보

상태: 채택(Accepted)  •  날짜: 2026-02-28

### 배경

- Holdings 입력은 KR은 6자리 코드, US는 `SYMBOL.EXCHANGE` 형식(`.NAS`, `.NYS`, `.AMS`)을 요구합니다.
- 사용자는 회사명은 알아도 “정규 티커 + 거래소 suffix”는 모르는 경우가 많아, 입력 과정이 번거롭습니다.
- 특히 `.NAS/.NYS`를 몰라서 이전 스캔 리포트를 열어 티커를 찾아오는 흐름이 반복됩니다.

### 결정

Holdings 입력 UX를 다음 3가지로 개선합니다.

1. **회사명/별칭 기반 티커 검색 + 자동완성**
  - Holdings 폼에서 회사명(예: “코스트코”)으로 검색하고 `COST.NAS` 같은 canonical 티커를 선택해 채웁니다.
2. **최근 buy 스캔 후보에서 바로 추가**
  - Holdings 화면에서 최근 buy 리포트 후보를 노출하고 클릭 1회로 ticker를 채웁니다.
3. **내부 티커 디렉토리(캐시) 도입**
  - buy 리포트의 `candidates[].{ticker,name}`를 누적해 “티커 ↔ 이름/별칭” 디렉토리를 유지합니다.
  - 저장소는 Supabase `runtime_state`(단일 row)로 하며, stale 조건에서 incremental로 갱신합니다.

### 결과/영향

- 장점
  - 사용자는 suffix를 외우지 않아도 되고, 리포트를 직접 뒤지지 않아도 됩니다.
  - 시스템 내부 데이터(리포트)로 디렉토리가 커지므로, 외부 심볼 검색 API에 의존하지 않습니다.
  - 별도 Supabase 테이블 마이그레이션 없이 빠르게 도입 가능합니다(`runtime_state` 재사용).
- 단점
  - 디렉토리 품질은 “스캔에 포함된 종목” 범위에 제한됩니다(미스캔/미등장 종목은 검색 불가).
  - 디렉토리 refresh 시 Supabase Storage 리포트 다운로드가 발생할 수 있어, 첫 로드 지연이 생길 수 있습니다(캐시/점진 갱신으로 완화).

### 대안 검토

- Supabase 신규 테이블(`ticker_directory`) 생성:
  - 장점: 서버-side 검색(ILIKE/FTS) 가능, 점진 업데이트 쉬움
  - 단점: 마이그레이션/인덱싱/권한 설계 비용 증가(초기 도입 과함)
- 서드파티 심볼 검색 API 연동:
  - 단점: 라이선스/비용/레이트리밋/정확도 문제 + 운영 복잡도 증가
- ticker 규칙 완화(예: `AAPL`만 입력 허용):
  - 단점: `.NAS/.NYS` 모호성(동일 심볼 상장/클래스 표기) 및 fail-closed 정책 약화
