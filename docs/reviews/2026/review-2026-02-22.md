# Swing Trading Report 코드베이스 심층 기술 리뷰

- 리뷰 일시: 2026-02-22
- 범위: 전체 저장소 (`sab`, `web`, `supabase`, `.github/workflows`, `docs`, `tests`)
- 수행 방식: 저장소 구조 전체 점검, 핵심 모듈 스키밍, 코드-문서 상호 검증
- 리뷰 관점: 정확성, 설계 안정성, 확장성, 추상화 적정성

## 핵심 진단

- 현재 가장 큰 위험은 **리포트 업로드/인덱싱 비원자성**입니다.
- 두 번째 위험은 **설정 정책(문서)과 실제 로더 구현의 불일치**입니다.
- 세 번째 위험은 **시장 데이터 신선도 보장 부재**로, 장애 시 오래된 데이터로 계속 의사결정할 수 있다는 점입니다.

## 상세 Findings

### 1) [CRITICAL] 리포트 게시가 원자적이지 않음 (업로드 성공 + 인덱스 실패 허용)

- 근거 코드:
  - `sab/report/supabase_storage.py:573`
  - `sab/scan.py:197`
  - `sab/sell.py:110`
  - `web/src/app/api/reports/route.ts:122`
- 근거 문서:
  - `docs/ARCHITECTURE.md:57`
- 문제:
  - (수정 전) 인덱스 upsert 실패(`SupabaseReportIndexError`)를 경고로 삼키고 storage key를 반환했습니다.
  - 그 결과 파이프라인은 성공처럼 끝날 수 있었고, 웹 목록 API는 `report_index` 기반이므로 리포트가 UI에서 사라질 수 있었습니다.
- 왜 막아야 하나:
  - 운영 관점에서 "생성됨/조회 안 됨" 상태는 탐지와 복구가 어렵고 신뢰성을 크게 훼손합니다.
- 권장 리팩터:
  - 스케줄/CI 실행에서는 인덱스 실패를 즉시 실패 처리.
  - 또는 outbox + 재시도 워커를 두고, 인덱스 반영 전까지 run 상태를 degraded/fail로 명시.
- 조치:
  - `ce26414`에서 GitHub Actions 실행은 인덱스 upsert 실패를 즉시 실패 처리하도록 변경.

### 2) [MAJOR] `config.yaml`/`.env` 충돌 금지 정책 미구현

- 근거 코드:
  - `sab/config.py:187`
- 근거 문서:
  - `docs/adr/ADR-0003-config-conflict-policy.md:12`
  - `README.md:43`
  - `docs/runbook.md:21`
- 문제:
  - 문서는 중복 키 충돌 시 fail-closed를 요구하지만, 구현은 단순 env 우선 fallback입니다.
- 왜 아픈가:
  - 동일 키 중복 시 실행 출처가 불명확해지고 재현성이 떨어집니다.
- 권장 리팩터:
  - 로딩 초기에 env/yaml 충돌 키 목록을 계산해 `ConfigLoadError`로 즉시 종료.

### 3) [MAJOR] 문서상 Fail-Closed와 달리 설정 파싱이 조용히 default로 회귀

- 근거 코드:
  - `sab/config.py:158`
  - `sab/config.py:574`
- 근거 문서:
  - `docs/ARCHITECTURE.md:124`
- 문제:
  - 숫자 파싱 실패/enum 오타가 런타임 오류 대신 기본값으로 흡수됩니다.
- 왜 아픈가:
  - 트레이딩 임계치가 조용히 바뀌는데도 눈치채기 어렵고, 결과 왜곡 원인 분석이 어려워집니다.
- 권장 리팩터:
  - 운영/CI 모드에서는 strict parsing을 적용해 잘못된 값은 즉시 실패 처리.

### 4) [MAJOR] 시장 데이터 캐시에 신선도 상한이 없어 오래된 데이터로 평가 가능

- 근거 코드:
  - `sab/market_data_pipeline.py:214`
  - `sab/market_data_pipeline.py:253`
- 문제:
  - 캐시를 우선 주입하고 API 실패 시 계속 캐시로 진행하지만, 최대 허용 stale 기준이 없습니다.
- 왜 아픈가:
  - 공급자 장애가 길어질수록 실제로는 오래된 캔들 기반 의사결정을 계속하게 됩니다.
- 권장 리팩터:
  - 시장(KR/US)별 세션 기준으로 최대 stale 허용치를 명시하고 초과 시 fail/degraded 처리.

### 5) [MAJOR] `/api/reports` 검색 경로가 취약하고 데이터 증가에 취약

- 근거 코드:
  - `web/src/app/api/reports/route.ts:135`
  - `web/src/app/api/reports/route.ts:164`
  - `web/src/app/api/reports/route.ts:171`
  - `web/src/app/api/reports/route.ts:226`
  - `web/src/lib/report-search-policy.ts:1`
- 문제:
  - 검색은 제한된 window를 순회하면서 hydration을 수행하고, 404가 아닌 단일 객체 오류가 전체 요청을 500으로 중단시킵니다.
- 왜 아픈가:
  - 리포트 수 증가 시 검색 비용이 커지고, 부분 손상 데이터 1건으로 전체 조회가 실패할 수 있습니다.
- 권장 리팩터:
  - 업로드 시점 인덱스 완전화를 원칙화하고, 조회는 partial failure tolerant(부분 결과 + 경고)로 전환.

- 권장 리팩터:

- 권장 리팩터:
