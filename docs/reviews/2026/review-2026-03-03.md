- 리뷰 일시: 2026-03-03
- 범위: 전체 저장소(`sab`, `web`, `.github/workflows`, `docs`, `supabase`, `tests`)
- 수행 방식: 저장소 구조 전체 점검, 핵심 모듈 스키밍, 코드-문서 교차 검증
- 리뷰 관점: 정확성, 설계 안정성, 확장성, 추상화 적정성
- 운영 가정(사용자 확인):
  - 웹은 별도 PRD 변경 전까지 `localhost` 단일 사용자 노출
  - `sab` 로컬 실행은 드문 편

## 핵심 진단

- 현재 가장 큰 리스크는 “리포트 업로드와 인덱스 반영의 비원자성”으로 인한 데이터 정합성 붕괴 가능성입니다.
- 웹 보안 경계는 현재 운영 가정에서는 실용적으로 동작하지만, 외부 노출 전환 시 즉시 취약해지는 구조입니다.
- 티커 디렉토리 검색 경로는 데이터 증가 시 지연과 비용이 급격히 증가할 수 있는 형태입니다.

## 상세 Findings

### 1) [CRITICAL] Storage 업로드와 `report_index` upsert가 원자적이지 않음

- 근거 코드:
  - `sab/report/supabase_storage.py:522`
  - `sab/report/supabase_storage.py:530`
  - `sab/report/supabase_storage.py:573`
  - `sab/report/supabase_storage.py:577`
  - `web/src/lib/reports-data.ts:114`
- 문제:
  - 오브젝트 업로드 성공 후 인덱스 upsert 실패 시(로컬 모드), 경고만 남기고 `None` 반환으로 종료됩니다.
  - 결과적으로 Storage에는 객체가 있고 `report_index`에는 없는 “고아 리포트”가 생길 수 있습니다.
  - 웹 목록은 index 기반이라 해당 리포트가 보이지 않으며, 운영자가 실패를 체감하기 어렵습니다.
- 왜 막아야 하나:
  - 데이터 정합성 깨짐이 누적되면 나중에 대량 정리/복구 비용이 크게 증가합니다.
  - `sab` 로컬 실행이 드물어도, 드물게 생긴 불일치가 더 오래 숨어 남습니다.
- 권장 리팩터:
  - 업로드를 “write contract”로 재정의: `(storage write + index upsert)`를 하나의 성공 단위로 취급.
  - upsert 실패 시 보상 삭제(delete uploaded object) 또는 outbox/retry 큐 도입.
  - 최소한 “index 누락 감지 리컨실 배치”를 추가.

### 2) [MAJOR] 로컬 요청/동일 출처 검증이 헤더 신뢰에 과의존

- 근거 코드:
  - `web/src/lib/local-request-guard.ts:86`
  - `web/src/lib/local-request-guard.ts:108`
  - `web/src/lib/same-origin.ts:60`
  - `web/src/lib/same-origin.ts:71`
  - `web/src/app/api/run/route.ts:21`
- 문제:
  - `host`, `origin`, `referer`, `sec-fetch-site` 기반 검증은 비브라우저 클라이언트에서 조작 가능합니다.
  - 현재는 localhost 전제라 실질 위험이 제한적이지만, 노출 범위가 바뀌는 순간 방어선이 급격히 약해집니다.
- 왜 아픈가:
  - “지금은 안전해 보이지만 운영 조건 변경 시 바로 사고나는” 전형적인 미래 부채입니다.
- 권장 리팩터:
  - unsafe 메서드에 CSRF 토큰을 1차 경계로 추가.
  - 헤더 검증은 보조 신호로만 사용.
  - 배포 전환 체크리스트(PRD/Runbook)에 “로컬 가드 의존 제거”를 강제 게이트로 명시.

### 3) [MAJOR] 티커 디렉토리 검색 경로가 요청 시점 동기 풀리빌드 구조

- 근거 코드:
  - `web/src/lib/ticker-directory.ts:322`
  - `web/src/lib/ticker-directory.ts:338`
  - `web/src/lib/ticker-directory.ts:401`
  - `web/src/lib/ticker-directory.ts:415`
  - `docs/holdings-ticker-lookup.md:115`
- 문제:
  - stale 판단 시 검색 요청 경로에서 최근 buy 리포트들을 순회하고, 각 리포트를 순차 다운로드해 전체 재빌드합니다.
  - 설계 문서의 incremental 의도와 달리 구현은 사실상 full rebuild입니다.
- 왜 아픈가:
  - 리포트 수/용량 증가 시 p95 지연 증가, API 타임아웃/변동성 증가.
  - “검색” API가 무거운 재색인을 동반하는 결합 구조가 됩니다.
- 권장 리팩터:
  - incremental merge(신규 key만 반영) 구현.
  - 요청 경로에서는 stale이면 기존 캐시 반환 + 백그라운드 refresh(비동기)로 분리.
  - 다운로드 동시성 제한(예: 4~8)과 실패 지표 로깅 추가.
