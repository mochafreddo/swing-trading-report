## 1) Executive Summary

- 전체 품질게이트/테스트는 강하지만, 운영에서 아픈 리스크 3개가 남아 있습니다.
- **[CRITICAL] Add-Buy 비멱등성**으로 중복 요청 시 보유 데이터가 조용히 오염될 수 있습니다.
- **[MAJOR] 부분 데이터 실패를 전체 실패로 승격**해 배치 내구성이 PRD 의도와 충돌합니다.
- **[MAJOR] 서버 아웃바운드 fetch 타임아웃 부재**로 상류 장애 시 API hang 위험이 큽니다.
- 보안 경계(인증 + same-origin + local guard)는 현재 “localhost 단일 사용자” 가정에서는 일관성 있게 적용되어 있습니다.
- 문서와 구현은 대체로 정합하지만, 런타임 버전 전략/운영 정책 일부는 명시적 의사결정이 더 필요합니다.

## 2) Findings (Severity 순)

### [CRITICAL] Add-Buy가 멱등하지 않아 재시도/중복 제출 시 수량·평단 오염 (Merge Blocker)

- Evidence:
  - 라우트가 요청마다 RPC를 직접 호출: `web/src/app/api/holdings/[ticker]/add-buy/route.ts:60`
  - RPC 시그니처에 멱등 키가 없음: `supabase/migrations/20260303000000_add_holdings_add_buy_rpc.sql:1`
  - RPC가 매 호출마다 누적 계산/업데이트: `supabase/migrations/20260303000000_add_holdings_add_buy_rpc.sql:65`, `supabase/migrations/20260303000000_add_holdings_add_buy_rpc.sql:87`
  - 테스트가 단발 성공/실패만 검증: `web/src/lib/__tests__/supabase-admin.test.ts:345`
- Impact:
  - 클라이언트 재시도, 네트워크 재전송, 사용자 더블클릭에서 같은 매수가 중복 반영됩니다.
  - 이후 `sell` 판단과 리포트 신뢰도가 장기적으로 붕괴됩니다.
- Recommendation:
  - API 입력에 `idempotency_key`(UUID) 또는 `Idempotency-Key` 헤더를 필수화.
  - `holdings_add_buy_v1`에 `p_idempotency_key` 추가.
  - `holdings_add_buy_events`(unique: `canonical_ticker + idempotency_key`) 도입 후 중복 키는 기존 결과 반환.
  - 회귀 테스트 추가: 동일 키 2회 호출 시 1회만 반영.
- Effort: M
- Confidence: High

### [MAJOR] 부분 수집 실패를 즉시 fatal 처리해 배치 내구성 저하 (Merge Blocker)

- Evidence:
  - scan 누락 데이터 시 fatal 설정: `sab/scan.py:56`, 호출 `sab/scan.py:234`
  - sell 누락 데이터 시 fatal 설정: `sab/sell.py:119`, 호출 `sab/sell.py:149`
  - PRD는 “부분 결과라도 리포트 생성”을 성공 지표로 명시: `docs/PRD.md:155`
- Impact:
  - 일부 종목 API 장애가 전체 배치 실패로 확대됩니다.
  - 자동 실행 운영에서 경보 피로 및 재실행 비용이 증가합니다.
- Recommendation:
  - 기본 정책을 “부분 성공 + 경고”로 전환하고, `min_data_coverage` 하한(예: 0.7) 미만만 fatal.
  - 리포트에 누락률/누락티커를 명시하고 종료코드를 coverage 기반으로 통일.
  - `scan`/`sell` 회귀 테스트에 “부분 실패 허용 경로” 추가.
- Effort: M
- Confidence: High

### [MAJOR] 서버 fetch 타임아웃 부재로 외부 장애가 API 지연으로 전파 (Merge Blocker)

- Evidence:
  - GitHub dispatch 호출에 timeout/signal 없음: `web/src/lib/github-actions.ts:103`
  - Supabase 호출 전반에도 timeout/signal 없음: `web/src/lib/supabase-admin.ts:131`, `web/src/lib/supabase-admin.ts:842`
- Impact:
  - 외부 서비스 지연 시 API 핸들러가 장시간 점유될 수 있습니다.
  - 운영 중 tail latency와 장애 복구 시간이 증가합니다.
- Recommendation:
  - `web/src/lib/http.ts`에 `fetchWithTimeout` 도입 (`AbortSignal.timeout` 기반).
  - 서버측 외부 호출 전체를 공통 유틸로 치환.
  - timeout을 504/명시적 에러 타입으로 매핑.
  - timeout 경로 테스트 추가.
- Effort: S~M
- Confidence: High

### [MAJOR] 비활성 holding(quantity<=0)도 sell 평가 대상에 포함됨

- Evidence:
  - 웹의 활성 기준은 `quantity > 0`: `web/src/lib/holding-activity.ts:11`
  - sell runtime은 수량 필터 없이 ticker 구성: `sab/sell_runtime.py:17`
  - 스케줄 sell holdings fetch도 수량 조건 없음: `.github/workflows/sell.yml:104`
  - 로더는 `quantity >= 0` 허용: `sab/holdings_loader.py:287`
- Impact:
  - 청산된 종목이 sell 리포트에 섞여 노이즈를 증가시키고 운영 판단을 흐립니다.
- Recommendation:
  - 1차: `sab/sell_runtime.py`에서 `quantity > 0`만 평가 대상으로 필터.
  - 2차: `.github/workflows/sell.yml` Supabase 쿼리에 `quantity=gt.0` 추가.
  - 메타에 `skipped_inactive_count`를 노출해 관측성 확보.
- Effort: S
- Confidence: High

### [MINOR] CI와 운영 워크플로우의 Python 버전 불일치

- Evidence:
  - CI는 3.13: `.github/workflows/ci.yml:30`
  - scan/sell 워크플로우는 3.14: `.github/workflows/scan.yml:37`, `.github/workflows/sell.yml:28`
  - 정적분석 타깃은 py313: `pyproject.toml:42`, `pyproject.toml:72`
- Impact:
  - “검증한 런타임”과 “실행 런타임”이 달라 런타임 특이 이슈를 뒤늦게 발견할 수 있습니다.
- Recommendation:
  - 단일 버전으로 정렬하거나 CI 매트릭스(3.13, 3.14)로 전환 후 단계적 단일화.
- Effort: S
- Confidence: Medium

### [MINOR] (가정) 로컬 가드는 운영 범위 확장 시 보안 모델 재정의가 필요

- Evidence:
  - 로컬 가드가 헤더 판별 중심: `web/src/lib/local-request-guard.ts:86`
  - 현재 배포는 localhost 바인딩 전제: `docker-compose.yml:28`
- Impact:
  - 외부 노출 환경으로 전환 시 현재 가드 모델만으로는 충분하지 않을 수 있습니다.
- Recommendation:
  - 운영 정책을 “로컬 전용”으로 고정하거나, 외부 노출 시 trusted proxy/네트워크 경계/CSRF 모델로 전환.
- Effort: S
- Confidence: Medium
