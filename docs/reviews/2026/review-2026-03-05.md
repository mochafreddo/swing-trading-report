# 기술 리뷰 보고서 (2026-03-05)

## 1) Executive summary
- 전체 위험도는 **중간 이상**입니다. 테스트/품질 게이트는 통과했지만, 운영 중 장애 비용이 큰 단일 장애점이 남아 있습니다.
- **머지 블로커 후보 1**: 로그인 스로틀이 Supabase에 하드 의존하여, Supabase 장애 시 관리자 로그인 자체가 500으로 막힙니다.
- **머지 블로커 후보 2**: `sab entry`가 가격 조회 계층이 사실상 죽은 상태에서도 `exit 0`을 반환해, 자동화에서 성공으로 오판됩니다.
- surprisingly good: `add-buy` 경로의 멱등성/동시성 제어(DB RPC + idempotency key + 충돌 코드 정규화)는 설계와 테스트가 잘 맞춰져 있습니다. (`web/src/app/api/holdings/[ticker]/add-buy/route.ts`, `supabase/migrations/20260304002000_add_holdings_add_buy_idempotency.sql`)
- 스코프 결정: 로컬 브랜치에 리뷰 대상 diff/PR이 없어 **whole-repo review**로 진행했고, 코어 플로우(`scan`, `sell`, `entry`, 웹 API auth/dispatch/holdings/reports)를 우선 샘플링했습니다.
- 품질 검증: `just quality`, `just ci-web` 실행 기준 통과(파이썬/웹 테스트, 린트, 타입체크, 빌드).
- 체크리스트 수행 상태:
  - 확인함: Correctness, Architecture, Security, Reliability/Observability, Testing/DX, 핵심 경로 성능 위험(정적 관점).
  - 확인 못함: 실거래 API/KIS·Supabase·GitHub Actions와의 **실서비스 연동 부하/장애 주입 테스트**, 장시간 soak 테스트, 다중 프로세스 동시 실행 벤치마크.

## 2) Findings (severity 순)

- [MAJOR] 로그인 경로의 Supabase 단일 장애점 (이 설계는 나중에 반드시 아픕니다)
- Evidence:
  - 런타임 상태 저장소 기본값이 `supabase`: `web/src/lib/login-throttle.ts:36-45`
  - 로그인 스로틀 체크/기록이 기본적으로 Supabase RPC 호출: `web/src/lib/login-throttle.ts:336-356`
  - Supabase 오류는 로그인 라우트에서 일반 500으로 전파: `web/src/app/api/auth/login/route.ts:109-125`, `web/src/app/api/auth/login/route.ts:128-145`
  - RPC 실패 시 예외 발생(타임아웃 포함): `web/src/lib/supabase-admin.ts:335-372`
- Impact:
  - 인증 자체가 외부 저장소 가용성에 묶여, Supabase 일시 장애/네트워크 이슈 때 관리자 로그인 불가.
  - 운영 관점에서 "관측/복구를 위한 진입 경로"가 먼저 끊겨 MTTR이 악화됩니다.
- Recommendation:
  - 코드 레벨 수정(구체):
    - `login-throttle.ts`에서 Supabase 경로 실패 시 `memory`로 degrade fallback (`assertLoginAttemptAllowed*`, `recordLoginAttemptFailure*`, `clearLoginAttemptFailures*`).
    - `SAB_LOGIN_THROTTLE_FAIL_MODE=strict|degrade` 플래그 추가(기본 `degrade`).
    - fallback 발생 시 구조화 로그 필드(`mode`, `error_type`, `throttle_key_type`) 남기기.
    - 테스트 추가: Supabase 5xx/timeout 시 로그인 성공 경로가 유지되는지, throttle 동작이 최소 보장되는지.
- Effort: M. Confidence: High.

- [MAJOR] `sab entry`의 시스템 단위 열화가 프로세스 성공 코드로 숨겨짐
- Evidence:
  - provider 초기화 실패/미설정 시 가격 조회 함수를 `None` 반환 람다로 대체: `sab/entry.py:442-443`, `sab/entry.py:457-458`
  - 가격 조회 실패는 row-level `REVIEW` + `system_issues`로만 누적: `sab/entry.py:231-248`
  - `system_issues`가 있어도 최종 `return 0`: `sab/entry.py:674-678`
  - 현재 테스트도 이 동작(가격 불가 + exit 0)을 기대: `tests/test_entry_command.py:233-249`
- Impact:
  - 스케줄러/자동화는 "성공"으로 판단하지만 결과는 실질적으로 사용 불가능한 `REVIEW` 묶음이 될 수 있습니다.
  - 장애 감지가 늦어지고, 매매 의사결정 신뢰도가 장기적으로 떨어집니다.
- Recommendation:
  - 코드 레벨 수정(구체):
    - `_make_price_lookup`에서 provider 미구성/초기화 실패를 `ValueError`로 명시 실패 처리.
    - `run_entry`에서 시스템 이슈 임계치 기반 종료코드 분리:
      - 예: `price_snapshot_unavailable_ratio >= ENTRY_FATAL_MISSING_PRICE_RATIO`면 `return 1`.
      - 기본값은 `1.0`(전량 실패)로 시작해 보수적으로 운용.
    - row action은 기존 계약대로 `REVIEW`를 유지하되, **프로세스 상태**는 실패로 노출.
    - 테스트 보강: "전량 가격 조회 실패 시 exit 1" 회귀 테스트 추가.
- Effort: M. Confidence: High.

- [MINOR] Python 버전 계약 불일치로 온보딩/재현성 저하
- Evidence:
  - README 요구사항: `Python 3.13+` (`README.md:17`)
  - 실제 프로젝트 요구사항: `>=3.14` (`pyproject.toml:6`)
  - toolchain도 3.14 고정: `mise.toml:9`
- Impact:
  - 신규 기여자가 README만 보고 3.13 환경을 구성하면 설치/실행 단계에서 실패.
  - 반복적인 환경 이슈 triage로 DX 비용 증가.
- Recommendation:
  - 즉시 하나로 정렬: README를 3.14+로 수정하거나, 실제 코드를 3.13 호환으로 낮추고 CI 매트릭스로 보장.
  - `just check-toolchain-contract` 같은 경량 검증(README/pyproject/mise 정합성) 추가.
- Effort: S. Confidence: High.

- [MINOR] API 보안 가드가 미들웨어와 라우트에 중복되어 정책 드리프트 위험
- Evidence:
  - 미들웨어에서 auth/same-origin 선검증: `web/middleware.ts:33-76`
  - 라우트 공통 가드에서 다시 auth/same-origin/local 검증: `web/src/lib/admin-api-guard.ts:23-29`
  - 주요 API 라우트들이 개별적으로 `enforceAdminApiGuard` 호출: 예) `web/src/app/api/run/route.ts:15`, `web/src/app/api/reports/route.ts:28`
- Impact:
  - 정책 변경 시 두 경로를 동시에 고쳐야 해서 회귀 위험 증가.
  - 테스트 픽스처/모킹도 중복 유지비가 커집니다.
- Recommendation:
  - 단일 정책 진입점으로 정리(미들웨어 중심 또는 route helper 중심 중 하나).
  - `/api/**` 보호 대상 라우트에 대해 contract test를 자동 생성/검증해 누락을 차단.
- Effort: M. Confidence: Medium.
