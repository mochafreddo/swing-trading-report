## Detailed Findings

### 1) Local-only 보호 경계가 `Host` 헤더 단일 신뢰에 의존

- Severity: **High**
- File/Location:
  - `web/src/lib/local-request-guard.ts:55`
  - `web/src/lib/local-request-guard.ts:58`
  - `web/package.json:7`
  - `web/package.json:9`
- Why it matters:
  - 로컬 제한 판단이 `host` 헤더 값에만 의존합니다.
  - 동시에 서버가 `0.0.0.0`에 바인딩되어 있어 네트워크 경계 설정이 잘못되면 보호 강도가 급격히 낮아집니다.
  - 현재는 `requireAdminAuth`/same-origin 체크가 있어 즉시 치명적 취약점은 아니지만, 인프라/프록시 변경 시 보안 가정이 깨지기 쉽습니다.
- Refactoring suggestion:
  - `Host` 검사 자체는 보조 방어로 유지하고, 필수 경계는 인증 토큰/세션 기반 인가로 고정합니다.
  - reverse proxy 환경을 고려해 신뢰 가능한 upstream만 `x-forwarded-*`를 처리하도록 명시합니다.
- Example improvement:
  - 라우트 공통 미들웨어에서 `requireAdminAuth` 성공 + CSRF/same-origin 검증을 1차 경계로 강제하고, local host 검증은 추가 hardening으로만 사용.

### 2) Holdings path ticker 검증 정책 불일치

- Severity: **High**
- File/Location:
  - `web/src/app/api/holdings/[ticker]/route.ts:22`
  - `web/src/lib/schemas.ts:71`
  - `web/src/lib/supabase-admin.ts:352`
  - `web/src/lib/supabase-admin.ts:386`
- Why it matters:
  - 생성(`POST`)은 `tickerSchema`로 강하게 검증하지만, `[ticker]` path 파라미터는 사실상 비어있지 않으면 허용합니다.
  - 이후 `ticker=eq.${ticker}` 형태로 쿼리 문자열을 조합하므로 정책 일관성이 깨지고, 이상 입력의 동작을 데이터 계층에 떠넘깁니다.
- Refactoring suggestion:
  - path ticker도 `tickerSchema`를 재사용해 동일 정책으로 normalize/validate 하세요.
  - URLSearchParams에 전달하기 전 입력 정책 단일화가 필요합니다.
- Example improvement:
  - `parseTicker`를 제거하고 `tickerSchema.safeParse(params.ticker)` 기반으로 400 반환.

### 3) Reports 검색이 데이터 증가에 선형적으로 악화

- Severity: **Medium**
- File/Location:
  - `web/src/lib/supabase-admin.ts:107`
  - `web/src/app/api/reports/route.ts:92`
  - `web/src/app/api/reports/route.ts:108`
  - `web/src/app/api/reports/route.ts:131`
- Why it matters:
  - 목록 조회를 위해 bucket key를 재귀적으로 순회하고, ticker 검색 시 후보 리포트를 개별 다운로드/파싱합니다.
  - 리포트가 누적될수록 응답 시간/요청 비용이 선형 증가합니다.
- Refactoring suggestion:
  - `report_index` 테이블을 두고 key/type/date/ticker를 사전 인덱싱하세요.
  - 조회 API는 Storage 직접 탐색 대신 SQL 쿼리로 전환하는 것이 맞습니다.
- Example improvement:
  - 리포트 업로드 시 인덱스 row upsert -> `/api/reports`는 인덱스만 조회 -> 상세 클릭 시에만 Storage 다운로드.

### 4) 로그인 스로틀/스토리지 키 캐시가 프로세스 메모리에 고정

- Severity: **Medium**
- File/Location:
  - `web/src/lib/login-throttle.ts:20`
  - `web/src/lib/login-throttle.ts:21`
  - `web/src/lib/supabase-admin.ts:166`
  - `web/src/lib/supabase-admin.ts:167`
- Why it matters:
  - 멀티 인스턴스/서버리스 scale-out 시 인스턴스마다 상태가 분리되어 일관성이 사라집니다.
  - 보안 제어(로그인 시도 제한)와 성능 캐시(키 목록)가 런타임 topology에 따라 예측 불가능해집니다.
- Refactoring suggestion:
  - throttle은 Redis/Upstash 등 외부 저장소로 이전하고, key cache는 TTL 캐시를 외부화하거나 인덱스 테이블 기반으로 제거합니다.
- Example improvement:
  - `assertLoginAttemptAllowed`를 Redis Lua 기반 rate-limit로 교체.

### 7) `KISClient`가 다중 책임을 가진 대형 클래스

### 8) 휴일 캐시 로더의 구조 검증이 약함

## Refactoring Roadmap

### Quick wins (1-2 days)

1. `holdings/[ticker]` path 입력을 `tickerSchema`로 통일해 CRUD 검증 정책 일치화.
2. `validate-env`를 기능별 필수값 검증으로 분리해 `build/start` DX 개선.
3. `middleware` matcher 설정으로 불필요 경로 실행 제거.
4. 휴일 캐시 로더에 구조 검증 추가(비정상 JSON fail-safe 처리).

### Mid-term improvements (1-3 weeks)

1. `reports` 조회를 인덱스 테이블 기반으로 전환해 Storage 전체 스캔 제거.
2. 로그인 스로틀/캐시를 외부 상태 저장소로 이전해 멀티 인스턴스 일관성 확보.
3. `scan/sell` 오케스트레이션 wrapper 단순화 및 공통 서비스 계층 정리.
4. API 보안 경계를 명시적으로 재정의(인증/인가/CSRF/로컬 제한 책임 분리).

### Long-term architecture improvements (1-2 months)

1. `KISClient`를 책임 단위 컴포넌트로 분해하고 공통 transport/retry 계층 표준화.
2. Python 애플리케이션을 `application/domain/infra` 경계로 재구성해 테스트/확장성 개선.
3. 리포트 생성 파이프라인을 "아티팩트 저장 + 메타 인덱스 갱신" 이벤트 흐름으로 고도화.
