# Swing Trading Report 코드베이스 심층 기술 리뷰

- 리뷰 일시: 2026-02-23
- 범위: 전체 저장소(`sab`, `web`, `.github/workflows`, `docs`, `tests`)
- 수행 방식: 저장소 구조 전체 점검, 핵심 모듈 스키밍, 코드-문서 교차 검증
- 리뷰 관점: 정확성, 설계 안정성, 확장성, 추상화 적정성

## 핵심 진단

- 가장 위험한 문제는 `cleanup`이 Storage만 삭제하고 `report_index`를 정리하지 않는 **인덱스/원본 불일치**입니다.
- `scan --limit`은 현재 “전체 평가 상한”으로 동작하지 않아 실행 비용/재현성에 직접 영향을 줍니다.
- 검색 API와 데이터 파이프라인은 동작은 하지만, 데이터 증가 시 비용이 빠르게 커지는 구조를 이미 갖고 있습니다.

## 상세 Findings

### 1) [CRITICAL] cleanup이 Storage만 삭제하고 `report_index`를 삭제하지 않음

- 근거 코드:
  - `.github/workflows/cleanup.yml:226`
  - `.github/workflows/cleanup.yml:228`
  - `.github/workflows/cleanup.yml:233`
  - `web/src/app/api/reports/route.ts:11`
  - `web/src/app/api/reports/route.ts:68`
  - `web/src/app/api/reports/detail/route.ts:68`
  - `web/src/app/api/reports/detail/route.ts:74`
- 문제:
  - cleanup 워크플로우는 Storage 오브젝트만 삭제하고, 같은 키의 `report_index` 행은 유지됩니다.
  - 목록은 `report_index` 기준이라 계속 노출되고, 상세 조회는 Storage 404로 실패할 수 있습니다.
- 왜 막아야 하나:
  - 사용자 관점에서 “목록에는 보이는데 열면 없음” 상태가 발생하고, 운영 측면에서 데이터 정합성 복구가 어려워집니다.
- 권장 리팩터:
  - cleanup에서 Storage 삭제 후 `report_index` 동시 삭제(또는 반대로 index-first 후 보상 트랜잭션)로 정합성 보장.
  - 최소한 정기 reconcile job을 추가해 dangling index를 정리.

### 2) [MAJOR] `scan --limit` 의미가 screener 활성화 시 깨짐

- 근거 코드:
  - `sab/__main__.py:57`
  - `sab/config.py:507`
  - `sab/config.py:508`
  - `sab/scan_screener.py:17`
  - `sab/scan_screener.py:65`
  - `sab/scan_screener.py:169`
  - `README.md:52`
- 문제:
  - `--limit`은 watchlist 로드 단계에서만 적용되고, 이후 screener 결과를 합치면서 총 평가 종목 수가 제한을 초과할 수 있습니다.
  - CLI 설명/문서는 “평가 상한”으로 읽히는데 실제 동작은 “watchlist 상한”에 가깝습니다.
- 왜 아픈가:
  - 실행 시간/외부 API 호출량/결과 재현성이 입력만으로 예측되지 않습니다.
- 권장 리팩터:
  - 정책을 명확히 둘 중 하나로 고정:
    - `--limit`을 전체 최종 ticker cap으로 강제
    - 또는 `--watchlist-limit`로 이름 변경하고 `--limit`은 총량 cap으로 신규 도입

### 3) [MAJOR] `holdings.yaml` 숫자 파싱이 fail-open(`0.0` 강제)

- 근거 코드:
  - `sab/holdings_loader.py:99`
  - `sab/holdings_loader.py:103`
  - `sab/holdings_loader.py:105`
  - `sab/holdings_loader.py:109`
- 문제:
  - `quantity`, `entry_price` 파싱 실패가 예외 없이 `0.0`으로 치환됩니다.
  - 입력 오류가 조용히 정상값처럼 흡수되어 잘못된 매도 판단으로 연결될 수 있습니다.
- 왜 아픈가:
  - 투자 의사결정 입력에서 침묵형 데이터 손상은 장애보다 더 위험합니다.
- 권장 리팩터:
  - 파싱 실패 시 `HoldingsLoadError`로 즉시 실패(fail-closed).
  - 오류 메시지에 항목 인덱스/티커/필드명을 포함해 수정 가능성 확보.

### 4) [MAJOR] 리포트 검색 경로가 규모 증가 시 비효율적(Offset + 매 페이지 exact count)

- 근거 코드:
  - `web/src/app/api/reports/route.ts:138`
  - `web/src/app/api/reports/route.ts:149`
  - `web/src/app/api/reports/route.ts:162`
  - `web/src/lib/supabase-admin.ts:419`
  - `web/src/lib/supabase-admin.ts:434`
- 문제:
  - 검색은 offset 기반으로 페이지를 순회하고, 각 요청마다 `Prefer: count=exact`를 강제합니다.
  - 데이터가 커질수록 페이지 스캔 + 정확 카운트 비용이 누적됩니다.
- 왜 아픈가:
  - 리포트 수가 증가하면 검색 응답시간과 DB 부하가 함께 악화됩니다.
- 권장 리팩터:
  - keyset pagination(정렬 키 기반)으로 전환.
  - 검색 경로에서는 exact count를 제거하거나 최초 1회/옵션성으로 축소.
